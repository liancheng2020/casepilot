# CasePilot 面试与演示

## 一分钟介绍

> 我做过订单小程序和支付状态相关业务，所以选了“客户付款成功但订单仍待支付”这个售后场景。CasePilot 是独立个人项目，不接公司生产数据。模型根据每轮订单、支付和回调查询结果决定下一步；缺少订单会追问，证据完整才提出处理建议。写操作由后端控制，运营确认后重新核验版本和规则，再以幂等方式执行、回查。我重点解决的不是让模型说得像客服，而是让建议能被验证、危险动作不能越权、重复确认和中断不会重复写入。

## 项目为什么值得做

客服不能只看一个订单状态就判断支付失败，通常需要核对支付渠道、回调和已有工单。固定规则能覆盖已知异常，Agent 的价值在于处理自然语言描述、信息缺失以及不同工具结果后的查询选择。

这里的 Agent 是“模型决策 + 工具反馈 + 受控循环”的调查系统，不是万能自动售后，也不是由模型定义退款规则。规则模拟器仅用于无 Key 演示与回归；只有 DeepSeek 模式才能展示真实模型如何选工具。

## 三分钟演示

运行 `npm run demo`，打开 http://localhost:5190。每次启动都是全新沙盒，下面三个案例各使用不同订单，避免前一次写入影响下一次结论。无 Key 时用规则基线讲解控制边界，不伪称真实模型选工具；真实模式需自己的模型配置和调用预算。

[观看自动录制演示](assets/interview-demo.webm)。视频为规则基线的三个完整处置路径，不是真实模型或真人业务审批录像。

### 正常闭环

1. 使用 `9223372036854775801`，客服调查回调缺失订单，展示状态仍为待支付，动作账本没有执行记录。
2. 查看“已查证事实 / 证据支持的判断 / 尚未确定”，点击来源图标打开实际引用的工具记录。模型解释单独标为未核验；若使用真实模型，指出工具批次和后续查询确实来自返回值。
3. 客服确认按钮不可用。切换运营演示身份后确认，订单变成已支付，版本递增，账本和回查结果可导出。
4. 说明角色切换只是沙盒演示，不等于真实企业登录。

### 审批时状态变化

使用 `9223372036854775808`，问题描述填“订单 9223372036854775808，支付后仍待支付，请核查”。提出对账建议后，从故障菜单注入并发关单。确认旧提案被拒绝，没有写订单；重新调查产生新证据和新提案，转为人工异常工单。批准工单后订单仍为关闭，不误改为已支付。解释“批准的动作对应某个业务快照，不是永久授权”。

### 结果未知与恢复

使用 `9223372036854775807`，问题描述填“订单 9223372036854775807，支付后仍待支付，请核查”。运营勾选演示响应丢失再确认，任务先显示待核对；点击核对查原动作账本，不重新执行。

要现场展示重启恢复：先记下启动时打印的数据目录，用 Ctrl+C 停止，再以 `DATA_DIR=<刚才的目录> PORT=5190 FEISHU_ENABLED=false AGENT_MODE=mock npm run dev` 重启。**不要再次运行 `npm run demo` 来恢复旧任务**，那会新建数据。恢复后核验后台订单与原动作 ID。故障是本地显式注入，不是声称完成了真实支付网络断连测试。

## 高频追问

### 为什么不用固定工作流？

如果只有标准支付补偿，固定流程更简单、可预测。这里让模型负责描述理解、补充信息、下一步查询和证据解释，把确定性业务规则留给后端。小规模案例验证的是能否沿工具反馈完成不同分支，不证明 Agent 比规则更有效，更不代表真实售后收益。

### 谁决定工具调用？模型还是 API？

API 接收、校验、存储和调度任务；Provider 请求模型，模型返回工具名与参数；ToolExecutor 校验并执行，再把结果回传模型。最终处置由后端审批服务执行，模型没有写入工具。

### 如何证明不是预录流程或伪 Agent？

看真实模式报告里的 assistant tool calls、对应 tool messages 和不同分支。回调缺失案例查询订单后再查支付、工单、规则和回调；支付失败案例结束调查，不生成相同的补偿提案。规则模式明确另列，不混入模型通过率。

### 模型伪造“已经批准”怎么办？

模型没有 approve 工具。审批 API 校验服务端身份、商家、提案 ID、有效期、订单和支付版本。客户端不能改提案参数；后端再次检查金额、状态、交易号等。模型文字不产生授权。

### 两次确认如何保证只执行一次？

同一提案有唯一动作记录和稳定幂等键；业务更新、动作记录、任务结果在同步 SQLite 事务内提交。第二次确认查到原记录，返回原结果。不同任务为同一订单创建工单时，执行阶段还会复查已有工单。

局限是所有业务数据在同一个本地数据库；远程接口不能靠这个事务保证一次执行，需要下游接受幂等键、提供结果查询，并实现 outbox 或补偿对账。

### 用户确认后订单被关掉怎么办？

提案记录订单和支付版本，执行时重新读取并比较。版本变化让原提案失效，不能用过期观察修改当前订单；重新调查的新 epoch 只能引用新证据。这比“按钮点过就执行”更重要。

### 模型超时、工具超时有什么不同？

模型 SDK 不隐藏重试，超时或 API 错误转人工且不会降级为模拟成功。只读工具错误作为反馈给模型，可在预算内重试；累计三个工具错误停止。写操作结果未知时不能照用查询重试策略，而应查原账本和业务状态。

### 为什么使用 SQLite、没有上 Redis 或 LangGraph？

首版单进程、小型任务，需要可查看的持久状态与同步事务；SQLite 更容易展示动作和状态原子提交。循环和状态边界不复杂，显式实现便于理解和测试。接入框架本身不是亮点，多实例和长任务需求成熟后再引入队列、检查点框架。

### 你有没有实际做 MCP 或飞书交互卡片？

没有。工具现在是本地 Function Calling；飞书通过官方 SDK 长连接接收私聊，采用中英文文字命令继续调查与审批，不是交互卡片。离线测试覆盖身份映射、消息重投、跨商家拒绝和审批复用。真实飞书与模型已验证缺号追问、补充后恢复同一任务、显式确认、执行回查和重复确认，原任务用了 5 次模型请求；确认由自动化使用本人授权的测试账号发送，不是企业独立审批。实际范围和误操作记录见 VALIDATION.md。

### 如何评价效果？

当前规则基线 12 个开发者案例用于回归；新一轮真实模型评测为 8 类已知案例各 2 次，16 次调查全部满足验收，使用 54 次模型请求。类别包括缺少信息、多候选、查询超时、已有工单、金额冲突和混入越权指令；第二轮改变投诉表达，每例使用新数据库。

检查的不只是回答文本，还包括预期处置分支、提案类型、审批前无写入、确认后的后台状态、重复操作和未知结果回查。评测里的审批是自动化测试身份，缺少信息和多候选只验收到追问暂停，不混称完整处置。

16/16 是开发者案例通过数，不是统计准确率。判断类型有独立预期；事实一致性检查复用领域函数，属于工程一致性回归而非独立语义裁判。没有真实用户样本，不能写“准确率100%”或“效率提升80%”。

进一步评估应固定案例和判定口径，加入未知场景、无答案与失败样本，独立复核解释是否被证据支持，记录人工修改、接管、时间和真实账单成本。

### 引用证据就能保证解释可信吗？

不能。现在不直接把模型长文本当结论：后端从所引成功快照提取事实，并检查 `finding` 和订单/支付版本，权威提案理由也由领域规则生成。模型原文另列且标明未做逐句语义核验。

例如渠道 `failed` 时，模型提交 `backend_paid` 会被拒绝；即使提交正确类型却写“已经到账”，展示的权威结论仍是后端生成的失败说明，原文只留作审核。这个边界由测试验证。它保护的是结构化主张，不是对整段文字做了可信性证明。

### 评测怎么防止无限消耗和挑选好结果？

每次请求前原子预留共享 SQLite 额度，失败也计数；重启保留总量，相同文件不允许隐式加上限。报告逐案例写盘，记录失败和跳过，CLI 只在所有计划案例通过时返回成功。本轮首批跑到 50 次时保留最后一项跳过，再单独补跑第二轮注入案例；两份报告都保留，不改写首批结果。SDK 重试关闭，额度边界与 API 失败计数有本地模拟协议测试。

## 简历可写与不可写

可写：

> CasePilot｜订单支付异常处置 Agent｜个人项目。基于 TypeScript、Vue 和 DeepSeek Tool Calling 实现多轮调查、订单澄清与受审批约束的处置；通过版本复核、事务账本和幂等键处理过期审批、重复操作及响应丢失，提供证据工作台与恢复验证。

只有亲自理解并能演示后再写。验证数量与范围参考 [VALIDATION.md](VALIDATION.md)，不能把自动化测试数当真实用户效果。

不可写：公司生产上线、真实退款、完整 MCP/Hermes 接入、企业飞书生产部署、生产级权限认证、通用 exactly-once、语义可靠性保证或没有测量的效率提升。飞书已在本人个人版应用验证私聊收发，具体业务范围见 VALIDATION.md。

面试前至少亲自修改一条业务规则、跑一个失败案例、追踪一次从 tool call 到 SQLite 的调用路径；解释自己的选择与不足，比背架构名词重要。
