# 架构与边界

## 主线

```text
Web / 钉钉消息
  -> 身份和商家范围 -> 持久化任务与去重回执
  -> Agent 循环：模型选择工具 -> 校验 -> 只读执行 -> 证据 -> 模型再决策
  -> 信息不足暂停 / 调查完成 / 人工接管 / 待确认提案
  -> 运营确认 -> 重新核验版本与规则
  -> 同一 SQLite 事务：业务写入 + 动作账本 + 任务状态
  -> 回查 / 结果未知时查原账本，不盲目重试
```

模型只决定调查工具、澄清和建议，后端决定是否允许执行。写动作不是模型可用工具；没有退款、Shell、任意 SQL 或直接修改支付状态的工具。

首版使用小型显式循环，不依赖 Hermes、LangGraph 或 MCP。当前工具注册是进程内 Function Calling，**不能宣称已经接入 MCP**。渠道和模型提供者可替换，业务规则与审批执行不随模型更换而变化。

## 代码职责

| 文件                  | 职责                                                       |
| --------------------- | ---------------------------------------------------------- |
| `server/agent.ts`     | 请求预算、动态工具反馈、批次限制、错误反馈、取消竞态       |
| `server/providers.ts` | 规则基线与 DeepSeek 原生工具调用；无隐藏重试和降级         |
| `server/tools.ts`     | 工具白名单、Zod 参数、唯一订单绑定、证据引用、建议而非写入 |
| `server/policy.ts`    | 对账资格与规则版本；提案内容摘要                           |
| `server/service.ts`   | 澄清、审批、拒绝、幂等执行、回查、恢复、串行调度           |
| `server/store.ts`     | SQLite 事务、动作唯一约束、任务 revision CAS、消息回执     |
| `server/dingtalk.ts`  | Stream 消息、组织与员工映射、文字命令、回执和回复地址限制  |
| `src/App.vue`         | 操作工作台、证据、审批、故障演示、真实/规则来源区分        |

## 谁拥有哪个状态

- 用户提供唯一订单号，或确认候选；模型不得从多个候选猜一个。订单 ID 始终为 19 位字符串，金额使用整数分。
- 查询只在当前商家范围内。订单与支付来自沙盒后台，不把客户“我已经付款”的描述当作支付成功。
- 模型每轮最多 4 个工具；澄清、提案、结束必须独立调用。参数、权限或证据错误作为工具结果反馈；累计 3 个工具错误转人工。
- 单任务请求、工具预算在重启和重新调查后不重置；请求发出前保存预算。终止后迟到的模型响应或异常不覆盖用户取消。
- 提案引用有效证据，包含订单版本、支付版本、规则版本、有效期和后端计算的 SHA-256 内容摘要。摘要不是数字签名，不能抵御有数据库写权限的攻击者。
- 运营确认只能提交当前提案 ID，不能趁确认修改动作参数。执行前重新检查身份、版本、有效期和业务规则。
- 对账条件包括订单待支付、渠道成功、订单和商家一致、金额币种一致、交易号存在；关单、退款或金额冲突不能直接改成已支付。
- 异常工单创建不改变订单；执行时重新查已有工单，复用原记录。唯一提案 ID 和稳定幂等键防止同一动作重复执行。

## 状态与恢复

`queued -> investigating -> needs_input / awaiting_approval / completed / handoff`

用户补充后重新入队；提案可以拒绝。确认后进入 `executing`，事务完成后为 `completed` 或演示 `result_unknown`。旧提案因状态或有效期冲突进入 `conflict`，重新调查生成新 epoch；旧证据仍保留审计，但不参与新提案。

任务、证据和工具消息保存在 SQLite。恢复调查时复用已保存结果，未落盘的只读查询可能再次执行。等待审批的任务不会被重启自动批准。未知结果按原提案查动作账本并核验后台，不重新生成幂等键。

本地沙盒的业务写入、账本、任务状态共享同步事务，写入回查失败会回滚。**这不是远程支付系统的分布式 exactly-once 实现。** 接真实业务接口时需要下游幂等协议、结果查询、事务 outbox 和对账机制。

单数据目录进程锁阻止多个服务同时调度；任务 CAS 防止旧对象覆盖新状态。首版不包含多进程工作队列、全局费用限额、生产监控或高可用保障。

## 钉钉入口

1. 在获得授权的测试组织创建企业内部机器人应用，启用 Stream 消息接收并发布到测试人员。
2. 配置 `DINGTALK_CLIENT_ID`、`DINGTALK_CLIENT_SECRET`、`DINGTALK_CORP_ID`。
3. 使用真实发送人的 `senderStaffId` 配置 `DINGTALK_ACTOR_MAP`，例如 `{"staff-test-cs":"service","staff-test-ops":"operations"}`；不能直接照抄示例员工 ID。
4. 配置测试人员可访问的 `PUBLIC_BASE_URL`；消息链接不携带令牌。设置 `DINGTALK_ENABLED=true`，重启常驻服务。
5. 先用合成订单试发，再核对任务、平台回执与后台结果。没有真实应用凭证时只运行离线适配器测试。

机器人文字命令：

```text
订单 9223372036854775801，客户说已支付，请查清楚。
补充 <任务UUID> <订单号或说明>
确认 <任务UUID> <提案UUID>
拒绝 <任务UUID> <提案UUID>
核对 <任务UUID>
```

服务只接受配置组织和员工，消息里的“管理员”声明不授予权限。消息去重持久化，ACK 在任务入库后返回；模型和回复发送不阻塞 ACK。回复 URL 只允许钉钉指定 HTTPS 主机和路径，不跟随跳转。

Stream 收消息、回复发送、组织权限是否配置正确，必须通过真实平台联调才能证明。通知暂未实现可靠 outbox；会话回复 URL 过期、发送失败或服务在 ACK 后重启可能丢通知，任务仍保存在 Web 工作台。首版不支持交互卡片和生产 SSO。

## 安全与可信边界

Web 的共享令牌和可切换演示身份只用于合成资料展示，**不是生产认证与角色管理**。远程部署需要 HTTPS 和访问控制；禁止接入真实订单、客户个人信息或生产支付凭证。

Zod 能校验字段结构，证据 ID 校验能确认来源存在；二者都不能保证模型的每一句解释被证据支持。模型建议仍需人工核查，严格业务规则保护写入，但不承诺完整抵御提示注入或任意语义误判。

请求次数在发出前记账，token 是服务返回 usage 的累计值；超时无法得到的用量未补计。没有把 token 估算成费用，避免对缓存与价格做无依据推断。
