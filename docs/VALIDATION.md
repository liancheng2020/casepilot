## 真实模型案例

模型：`deepseek-flash`，原生 Tool Calling，SDK `maxRetries=0`，单次超时 25 秒，非思考模式。

| 案例               | 模型请求 | 工具调用 | 累计返回 token | 调查耗时 | 结果                                                           |
| ------------------ | -------: | -------: | -------------: | -------: | -------------------------------------------------------------- |
| 支付成功但回调缺失 |        4 |        6 |          9,166 |  5.72 秒 | 生成对账提案；模拟审批后核对原执行记录，订单已支付且仅执行一次 |
| 支付渠道失败       |        3 |        4 |          6,531 |  4.80 秒 | 依据渠道状态说明失败，没有修改订单或创建补偿动作               |

耗时包括调用与本地调查，受网络影响；token 是多轮 API 返回 usage 的累计值，非单次上下文长度、缓存费用或真实收费估算。最初失败的请求没有可用 usage。

两个模型案例共享开发时已知业务规则，只有投诉发送给模型，没有发送验收答案；不代表独立未知问题集上的统计效果。真实验证后又补了取消竞态、回查和去重回归，最终版本做了离线测试和界面验证，没有继续消耗 API 额度。

## 规则案例构成

12 个固定案例：回调缺失、支付失败、订单已关闭、后台已支付、金额冲突、已有工单、缺少订单号、多候选、支付处理中、退款、跨商家和一条提示注入输入。

检查目标分支、动作类型、审批前无写入、未泄露其他商家、动作次数和最终业务状态。规则模式可复现，但没有模型随机性，不能把 12/12 转为 LLM 成功率或提示注入防御保证。

## 界面端到端

- 客服身份无法审批；运营才可确认。
- 工具证据可以打开核查。
- 注入响应丢失后显示未知结果，而非声称已完成。
- 实际停止并重启测试服务，SQLite 留存任务并核验原动作。
- 并发关单后旧提案失效，不写订单。
- 重新调查产生新异常工单分支。
- 案例与订单页面可访问，执行记录可以导出。
- 1440px 桌面和 390px 手机截图检查；手机无页面横向溢出，刷新图标居中，无浏览器运行时错误。

本机新 Playwright Chromium 下载超时，界面验证使用已安装的 Chrome for Testing，通过 `CHROMIUM_EXECUTABLE_PATH` 指定；没有因此跳过界面测试。

## 未验证与限制

尚无真实钉钉测试应用联调、真实商家用户评测、大规模未知案例、生产权限认证、多实例并发、远程写接口幂等和可靠通知 outbox。没有自动证明自然语言解释被证据支持；也没有建立缓存计价后的成本指标。
